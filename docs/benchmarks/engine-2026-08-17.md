## What this means (plain English)

Three questions, three answers:

**1. Does the AI get dumber as the repository grows? No.**

The model caught the seeded drift at all four sizes — 22 files or
3,900 files, same result. The per-review context stays flat at ~4.6 KB
from 110 files up, because the engine never shows the model "the whole
repo": it slices the work one boundary at a time with hard caps
(≤ 4 KB contract, ≤ 6 KB code, ≤ 10 files). The repository grows; the
review doesn't. And the deterministic scan catches drift *before* the
AI even thinks, so the guarantee never depends on model quality.

One honest caveat from this run: on the smallest repo (22 files) the
model **hallucinated** — it invented a file path that doesn't exist.
That's exactly the failure mode the supervisor and the deterministic
scan exist for: a made-up path fails `acc check` and scores below the
85% approval threshold, so it never gets written. It's a reminder that
the AI layer is fallible and the deterministic layer is the safety
net — not the other way around.

**2. Do the ACC files (contracts + memory) actually help? Yes — about 2×.**

Same code, two setups: with ACC contracts + memory the model reported
**2 drift items**; with only a bare `AGENTS.md` it reported **1**. The
written constraints give the AI concrete things to check, instead of
making it guess intent from code alone. It's not the difference between
finding drift or not (the deterministic layer guarantees that) — it's
the difference between a thin review and a thorough one.

**3. Does the graph stay small on big repos? Yes — it's flat.**

~380 bytes per file and ~180 bytes per item from 22 files to 3,908
files — the size barely moves. That's because the graph stores **no
prose at all**: only ids, types, hashes and provenance. It's a routing
table that points at the filesystem, not a copy of it. A 4,000-file
repo yields a ~1.5 MB index, and that index stays queryable and
cheap at any scale.

**Bottom line:** the design goals hold under measurement — the AI phase
is size-independent (budgets + slicing), the ACC files measurably
improve review quality, and the graph is a tiny, constant-cost index
that won't bloat as the codebase grows.
